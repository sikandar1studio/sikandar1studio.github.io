How to brief a custom web application

A useful software brief starts with a task someone needs to complete. Before choosing a framework or listing features, explain what happens today, what gets in the way and what a better result would look like.

By Sikandar Riaz4 November 20264 min read

THE STARTING POINT

Bring one real workflow, one representative input and a clear description of the result you need. That is a stronger starting point than a long list of disconnected features.

1. Describe the job before the screens

Write down a complete example of the work as it happens now. Who starts it? What information do they receive? What decisions do they make? Where does the finished result go? A small, concrete example helps reveal missing steps that a general request such as ‘build a dashboard’ leaves open.

If you want a tool for reviewing creative assets, for example, describe how a file arrives, who reviews it, what makes it acceptable and how the approved version is delivered. This gives the interface a purpose and makes it easier to decide which features belong in the first release.

2. Identify users, permissions and devices

A tool for one person has different needs from a shared workspace. List the people or roles involved and what each one should be able to see or change. Make account ownership, administrative actions and access to sensitive material explicit rather than leaving them to be decided during development.

Also describe where the application will be used. A workstation, a phone and an exhibition touchscreen place different demands on layout and interaction. Include any browser, network or hardware constraints you already know about, and mark the unknowns that need investigation.

3. Bring representative inputs and outputs

Share a safe sample of the information the application will handle: a spreadsheet, a typical asset, a sample form or an export specification. Use redacted or synthetic data when the real material is private. Explain which fields are required and what should happen when a file is missing, invalid or too large.

Integration names alone are not enough. Identify what information needs to move between systems, which account owns access and whether the relevant API or export is available. A dependency that has not been checked should remain an open question in the brief.

4. Separate the first release from later ideas

Choose the smallest complete journey that would make the tool useful. ‘Complete’ matters: a polished input screen without a usable output may not solve the underlying task. Put essential behavior, helpful additions and future ideas into separate lists, then agree what the first delivery actually includes.

Image to 3D Studio offers a useful interface example. Its documented workspace puts the reference, generation controls, model review and export in one sequence. The case study shows how these stages are organized visually; it does not provide a generation-performance benchmark. That distinction between a demonstrated interface and a tested production capability should also be clear in a new project brief.

5. Define what a successful handoff looks like

Replace ‘it should work well’ with a few observable checks. A user can complete the main task, understand an error, recover from a missing input and find the result. If several roles are involved, specify which actions must be unavailable to each role. Agree the devices and environments in which these journeys will be checked.

Development also needs a destination. Establish who owns hosting and third-party accounts, how credentials will be managed, whether source files are included and what documentation is needed. Maintenance and future changes should have an agreed arrangement; they are not implied by the presence of a finished interface.

A short brief you can use

A first conversation does not need a formal specification. Send the points below, together with a representative example. The aim is to expose the important decisions early, while keeping room to refine the solution.

  • The task: what someone needs to achieve and how they do it now.
  • The users: their roles, devices and access requirements.
  • The material: sample inputs, expected outputs and integrations.
  • The first release: the essential end-to-end journey.
  • The handoff: launch constraints, hosting ownership and support needs.
